Research date: 2026-11-02. Reliability labels used throughout:
**[Official]** = Meta-authored page; **[Press]** = reputable outlet reporting; **[Leak/Docs]** = leaked or internal documents reported by press; **[3P-teardown]** = single independent researcher's analysis (unverified by others); **[Aggregator]** = secondary blog/wiki (lower reliability); **[Inference]** = my reasoning.

## Q1. What exactly is "Meta Muse"? Disambiguation, timeline, open vs closed

### Takeaway
"Muse" at Meta is two related things, both from Meta Superintelligence Labs (MSL): (1) the **Muse model family** (Muse Spark, launched 2026-04-08, proprietary; later 1.1/1.2/1.3, plus open-weight Muse Glimmer and Muse Spark Open), and (2) **Muse, the personal AI agent product** (internal codename "Hatch"), launched in the US 2026-09-08, which runs on Muse Spark inside a per-user cloud VM. Microsoft's "Muse" is an unrelated 2025 gameplay world model (WHAM). High confidence on this disambiguation.

## Q3. Architecture as assistant/agent: tool loop, memory, scheduling/proactivity, sandboxing, multi-agent, surfaces

### Takeaway
Muse is a per-user, always-on cloud Linux VM agent: the LLM harness runs in a `systemd-nspawn` "runtime cell," and an independent **Sentinel** service is the sole authority for network egress and connector actions (allow/deny/ask with scoped grants), with surrogate-token credential injection, eBPF taint tracking, classifier ensembles for prompt injection, a sandboxed browser sub-agent, and file-based + Postgres-indexed memory with claim verification and "dream" jobs. meta.ai chat itself uses a namespaced tool loop (browser.*, meta_1p.*, container.*, subagents.spawn_agent).

### Cited Findings
**meta.ai chat harness (Muse Spark, April 2026)**
- [3P] Tools: `browser.search/open/find`; `meta_1p.content_search` (semantic search over Instagram, Threads, Facebook posts visible to the user, since 2025-01-01); `meta_1p.meta_catalog_search`; `media.image_gen`; `container.python_execution` (remote sandbox, Python 3.9.25, files persist at `/mnt/data/`); `container.create_web_artifact` (sandboxed iframe HTML/SVG); `container.download_meta_1p_media`; `container.file_search`; `container.view/insert/str_replace`; `container.visual_grounding` (point/bbox/count, native model ability invoked via tool + custom system prompt); `subagents.spawn_agent` (returns sub-agent's final text); `third_party.link_third_party_account` (Google Calendar, Outlook Calendar, Gmail, Outlook) — [Simon Willison](https://simonw.substack.com/p/metas-new-model-is-muse-spark-and)
- [Official] Meta AI "can launch multiple subagents in parallel" for complex questions; Instant and Thinking modes; Shopping mode mixing Marketplace listings + web; "side chats" in group chats; @meta.ai in Threads — [about.fb.com Apr 2026](https://about.fb.com/news/2026/04/introducing-muse-spark-meta-superintelligence-labs/)
- [Official] Surfaces: Meta AI app/meta.ai first; May 2026 "everywhere" update to WhatsApp, Instagram, Facebook, Messenger, Threads; Ray-Ban Meta/Oakley Meta glasses in US/Canada, Meta Ray-Ban Display later — [about.fb.com Apr 2026](https://about.fb.com/news/2026/04/introducing-muse-spark-meta-superintelligence-labs/)

**Muse agent sandboxing & permissions**
- [Official] Dedicated VM per user is "system of record"; "two isolated security domains on one box, not an LLM powered agent with root"; runtime cell via `systemd-nspawn` (unprivileged root mapping, own rootfs, virtual NIC, filtered syscalls e.g. no `io_uring`, dropped `CAP_SYS_PTRACE`/`CAP_NET_ADMIN`); services outside the cell: `hatch-safety` (classifiers on inference I/O), `privsep` workers (connector logic), `hatch-authd` (credential store, surrogate tokens), Sentinel, Postgres, inference/telemetry proxies; IPC over Unix sockets with SO_PEERCRED ACLs — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] "Muse proposes actions, but only Sentinel can grant permission." Sentinel receives connector, method, action class, scope, user context; generates a user-visible purpose; returns allow/deny/ask; L4+L7 egress checks (host, resolved/final IP, port, method, path, decoded body); SSRF protection — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] Approvals go to the client UI, not the chat, and the answer returns straight to Sentinel; grant types: one-time, session, task-scoped, time-bounded, perpetual, bound to connector/destination + use case, later calls must match exactly; read-only / previously-allowed / low-risk proceed silently — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] Surrogate tokens: "The agent never sees real tokens"; real credentials swapped in at the network boundary after authorization — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] Tainted egress: each tool process starts clean, becomes tainted after reading user data; tainted processes lose auto-allow (eBPF cgroup + LSM hooks) — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] Least privilege below OAuth scope (e.g. Gmail read without settings access); connector CLIs in the cell pass typed args + FDs over Unix socket to sandboxed workers; Muse can write custom connectors using SKILL instructions; email connector strips OTPs, reset links, magic links — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] Prompt injection: model training + harness labels external data as untrusted + independently trained classifier ensemble on files/tool results + agentic red teaming + approvals for data leaving the VM — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] Browser: real Chromium behind virtualization; user can watch and take over; browser sub-agent sees accessibility tree, cannot run JS, DevTools disabled; CDP broker outside cell; agent paused during takeover/credential fill; checkout triggers exact-detail approval; single-use virtual cards bound to merchant/amount/time — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)
- [Official] Users pick per-app access level (e.g. read mail vs send), can revoke; audit trail of past and planned actions; planned "Muse Confidential VM" with user-held key — [about.fb.com Sept 2026](https://about.fb.com/news/2026/09/introducing-muse); bug bounty up to $300k ($130k for single-user prompt injection) — [Meta research blog](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

### Inferences
- Muse's core security idea is that the LLM is untrusted: permission, credentials, egress, and approval UI are all outside the model's process and outside the chat transcript.
- The memory design (human-readable Markdown as source of truth + DB index + claim provenance/verification + explicit retraction) addresses hallucinated memories, a known failure in chat-memory systems.
- The "human agent layer" and the Amazon block show that agent provenance and disclosure (who/what actually acted, and does the agent identify itself to third parties) matter as much as capability.

### Gaps
- No official detail on how cron/background tasks are approved or rate-limited, or how Sentinel policy applies to unattended runs.
- No official confirmation of the Postgres memory schema or the claims-verification job (single-researcher source).
- Unclear whether Muse in WhatsApp sends proactive (business-initiated) messages and how that interacts with WhatsApp's 24-hour window rules.

## Q4. Concrete design lessons for OpenCompany

### Takeaway
Muse is the closest large-scale analogue to OpenCompany (persistent agent, chat surfaces including a messaging app, background work, connectors/MCP, approvals, memory). Its most transferable ideas are out-of-band permissioning with scoped grants, credential surrogates, taint-aware auto-approval, inspectable file-based memory with provenance, rate-limited proactivity, and replayable event logs.

### Inferences (design lessons for OpenCompany)
1. **Move approval authority out of the model loop.** Treat the approval/permission service as the only component allowed to authorize external mutations (MCP write tools, Telegram sends to new chats, HTTP egress). The agent proposes; a deterministic policy layer decides allow/deny/ask. Approval prompts must be delivered as structured UI (web card, Telegram inline buttons), never parsed from free-text chat replies, and the decision should go directly to the policy service, not back through the LLM.
2. **Scoped, exact-match grants.** Support one-time, run/session, task-scoped, time-bounded, and standing grants, bound to (workspace, agent, tool/connector, action class, destination). Re-check on every call; do not let a grant for "read Gmail" cover "send Gmail." Separate read vs write tool classes per MCP server even where the upstream OAuth scope does not.
3. **Never give the agent raw secrets.** Inject credentials at the tool/transport boundary (surrogate placeholders in the agent context, resolved server-side), consistent with existing secret-handling expectations. Strip OTPs/reset links/magic links from ingested email/messages before they enter context.
4. **Taint-aware auto-approval.** Once a run has read untrusted or private data (web pages, inbound Telegram from non-owners, email bodies), downgrade auto-allow policies for outbound actions in that run. This is a cheap application-level version of Meta's eBPF taint tracking.
5. **Label untrusted content and run an independent injection check.** Wrap tool results/inbound messages as untrusted in prompts and optionally run a separate classifier/model on tool outputs before high-risk actions; do not rely on the main model alone.
6. **Memory as inspectable files plus provenance.** Keep a human-readable memory document per agent/user (fits OpenCompany's identity-file approach and VFS), back it with a searchable index, and store each memory as a claim with source message IDs, confidence, and `supersedes` links; run a scheduled verification pass and support explicit "forget" that retracts claims and reindexes. Scope all memory by workspace.
7. **Proactivity with hard limits.** Scheduled automations and agent "check-ins" should only message threads the human started (or explicitly subscribed to), cap unanswered follow-ups (Omni's rule is one), avoid sensitive topics unless user-raised, and record why each proactive message fired. Background "dream"/reflection jobs should write receipts (what changed in memory/workspace) users can audit.
8. **Audit trail of past and planned actions plus replayable event logs.** Surface planned actions before execution and keep a JSONL-style, replayable event log of every tool call, subagent spawn, steer and cancel; support resume after crash.
9. **Subagent isolation and escalation.** Give write-capable subagents isolated workspaces (worktree/VFS sandbox), cap concurrency, and require subagents to stay in scope and escalate rather than widen their own permissions. Parent agents get status/wait/cancel controls.
10. **Plan-then-approve for long tasks.** A plan artifact that stops for human approval before mutations maps naturally onto OpenCompany tasks and approvals.
11. **Disclosure and provenance to third parties.** Agents acting externally (Telegram, email, web) should identify as agents; record whether a human or an agent performed each step (cf. Muse's undisclosed human call layer).
12. **Share links and exports are attack surface.** Use unguessable, revocable, authenticated share links (not enumerable subdomains); treat "export my files" tool paths as data-exfiltration paths subject to approval.
13. **Assume prompts and tool manifests are public.** Meta's tool list was obtainable by asking. Put no security-relevant secrets or policy in prompts; enforce in code.
14. **Provider-agnostic model catalog entry.** Muse Spark 1.x via Meta Model API (described as OpenAI-compatible) and open-weight Muse Glimmer / Muse Spark Open can be added through the app-owned provider/model catalogs rather than hardcoded.

### Gaps
- No public data on Muse's real-world approval fatigue rates or how often users choose perpetual grants, which would inform default grant scopes.
- No public evaluation of Muse's prompt-injection classifier efficacy.
